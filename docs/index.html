Prerequisites & Host Setup
Prepare your host machine and understand the hardware you need before building anything.
⏱ Week 1 · Estimated 2–3 days
1.1 Hardware Requirements & Planning ▾

Minimum Host Specs

  • RAM: 16 GB minimum — 32 GB strongly recommended (5 VMs running simultaneously)
  • CPU: Modern quad-core with VT-x/AMD-V virtualization enabled in BIOS
  • Storage: 250 GB free SSD space — spinning disks will make the lab painfully slow
  • Network: Single NIC is fine — all traffic stays in virtual networks

VM Resource Allocation Plan

# Splunk Server (Ubuntu) RAM: 4–8 GB CPU: 2–4 cores Disk: 60 GB # Windows Server 2022 (DC) RAM: 2–4 GB CPU: 2 cores Disk: 50 GB
# Windows 10/11 (Target) RAM: 2–4 GB CPU: 2 cores Disk: 50 GB # Kali Linux (Attacker) RAM: 2–4 GB CPU: 2 cores Disk: 30–40 GB
⚠ Splunk needs RAM most. Give it as much as you can spare — it processes high log volumes and slow RAM causes indexing delays.

2.2 Deploy Windows Server 2022 — Active Directory DC ▾

Active Directory Setup Steps

  • Install Windows Server 2022, set static IP: 192.168.10.20
  • Open Server Manager → Add Roles → Active Directory Domain Services
  • Promote to Domain Controller — create new forest (e.g., soc.local)
  • Set DSRM password, complete promotion and reboot
  • Create Organizational Units: IT, HR, Finance, Admin
  • Create test user accounts in each OU (e.g., jsmith, tuser, badactor)
# PowerShell — Create test users for attack simulation New-ADUser -Name "John Smith" -SamAccountName "jsmith" ` -AccountPassword ("Password123!" | ConvertTo-SecureString -AsPlainText -Force) ` -Enabled $true -Path "OU=IT,DC=soc,DC=local"
⚠ Use weak passwords like "Password123!" intentionally — these are targets for your brute-force simulations. Never reuse these anywhere real.
2.3 Deploy Windows 10/11 Client & Join Domain ▾

Domain Join Steps

  • Set static IP 192.168.10.30, DNS pointing to DC: 192.168.10.20
  • System → Advanced → Computer Name → Change → Domain: soc.local
  • Authenticate with domain admin credentials, reboot
  • Log in with domain user (e.g., soc\jsmith)

Enable Advanced Audit Policies via GPO

# On Domain Controller — Group Policy Management # Default Domain Policy → Computer Config → Policies # → Windows Settings → Security Settings → Advanced Audit Logon/Logoff: Audit Logon — Success + Failure Account Logon: Audit Credential Validation — Success + Failure Object Access: Audit File System — Success + Failure Process Tracking: Audit Process Creation — Success Privilege Use: Audit Sensitive Privilege Use — Success + Failure Account Mgmt: Audit User Account Management — Success + Failure
2.4 Deploy Kali Linux (Attacker Machine) ▾

3.2 Install Sysmon on Windows Machines ▾

What is Sysmon?

  • System Monitor — a Windows service that logs granular events: process creation, network connections, file changes, registry modifications, driver loads
  • Standard Windows Event Log misses most attack telemetry — Sysmon fills that gap
  • Use SwiftOnSecurity config or Olaf Hartong's modular config for MITRE ATT&CK alignment

Installation (PowerShell — run as Administrator)

# Download Sysmon and the SwiftOnSecurity config # Place both in C:\Sysmon\ # Download SwiftOnSecurity config: # https://github.com/SwiftOnSecurity/sysmon-config # Install with config .\Sysmon64.exe -accepteula -i sysmonconfig-export.xml -n # Verify it's running Get-Service Sysmon64 # View logs in Event Viewer: # Applications and Services → Microsoft → Windows → Sysmon → Operational

Key Sysmon Event IDs to Know

  • Event ID 1 — Process Create (command line, hashes, parent process)
  • Event ID 3 — Network Connection (source/dest IP, port, process)
  • Event ID 7 — Image Loaded (DLL loaded into process)
  • Event ID 10 — Process Access (credential dumping indicator)
  • Event ID 11 — File Created
  • Event ID 13 — Registry Value Set
  • Event ID 22 — DNS Query
3.3 Install Splunk Universal Forwarder on Windows ▾

Install Universal Forwarder

# Run the MSI installer on Windows 10/11 and Server 2022 # During install wizard: Receiving Indexer: 192.168.10.10:9997 # Set local admin credentials for the forwarder service

Create inputs.conf to Forward Sysmon + Security Logs

# File: C:\Program Files\SplunkUniversalForwarder\etc\system\local\inputs.conf [WinEventLog://Security] disabled = 0 index = endpoint renderXml = true [WinEventLog://Microsoft-Windows-Sysmon/Operational] disabled = 0 index = endpoint renderXml = true sourcetype = XmlWinEventLog:Microsoft-Windows-Sysmon/Operational [WinEventLog://System] disabled = 0 index = endpoint [WinEventLog://Application] disabled = 0 index = endpoint

Create outputs.conf to Point at Splunk

# File: ...\SplunkUniversalForwarder\etc\system\local\outputs.conf [tcpout] defaultGroup = splunk_indexer [tcpout:splunk_indexer] server = 192.168.10.10:9997

Restart Forwarder & Create Index in Splunk

# PowerShell (restart forwarder) Restart-Service SplunkForwarder # In Splunk Web UI: # Settings → Indexes → New Index → Name: endpoint
3.4 Configure Linux Log Forwarding (Ubuntu) ▾

Option A — Splunk Universal Forwarder (Recommended)

# Download Linux forwarder .deb wget -O splunkforwarder.deb https://download.splunk.com/products/universalforwarder/releases/9.3.0/linux/splunkforwarder-9.3.0-linux-amd64.deb sudo dpkg -i splunkforwarder.deb cd /opt/splunkforwarder/bin sudo ./splunk start --accept-license sudo ./splunk add forward-server 192.168.10.10:9997 sudo ./splunk add monitor /var/log/auth.log -index linux_logs sudo ./splunk add monitor /var/log/syslog -index linux_logs

4.1 Brute Force Attack — Hydra via Kali ▾

Run the Attack (from Kali — 192.168.10.50)

# Brute force RDP on Windows target hydra -l jsmith -P /usr/share/wordlists/rockyou.txt rdp://192.168.10.30 # Brute force SMB on Domain Controller hydra -l Administrator -P /usr/share/wordlists/rockyou.txt smb://192.168.10.20 # SSH brute force on Ubuntu hydra -l ubuntu -P /usr/share/wordlists/rockyou.txt ssh://192.168.10.40

Detect in Splunk — Look for Event ID 4625 (Failed Logons)

index=endpoint EventCode=4625 | stats count by Account_Name, IpAddress, _time | where count > 5 | sort -count
# After brute force succeeds — spot the successful logon index=endpoint EventCode=4624 Account_Name=jsmith | table _time, host, Account_Name, Logon_Type, IpAddress
⚠ Look for 50+ failed EventCode 4625 in rapid succession from a single source IP — that's your brute force fingerprint. Followed by a 4624 = successful compromise.
4.2 Atomic Red Team — MITRE ATT&CK Simulations ▾

Install Atomic Red Team (Windows Target — PowerShell as Admin)

# Set execution policy Set-ExecutionPolicy Bypass -Scope CurrentUser -Force # Install NuGet and the Invoke-AtomicRedTeam module Install-PackageProvider -Name NuGet -Force Install-Module -Name invoke-atomicredteam,powershell-yaml -Force Import-Module invoke-atomicredteam # Download the atomic test definitions IEX (IWR 'https://raw.githubusercontent.com/redcanaryco/invoke-atomicredteam/master/install-atomicredteam.ps1' -UseBasicParsing) Install-AtomicRedTeam -getAtomics

Run Key MITRE ATT&CK Techniques

# T1136.001 — Persistence: Create Local Account Invoke-AtomicTest T1136.001 # T1059.001 — Execution: PowerShell (encoded command) Invoke-AtomicTest T1059.001 # T1003.001 — Credential Access: LSASS Memory Dump Invoke-AtomicTest T1003.001 # T1053.005 — Persistence: Scheduled Task Invoke-AtomicTest T1053.005 # T1197 — BITS Jobs (LOLBin technique) Invoke-AtomicTest T1197 # Always clean up after each test Invoke-AtomicTest T1136.001 -Cleanup

Detect T1059.001 (Encoded PowerShell) in Splunk

index=endpoint sourcetype=XmlWinEventLog:Microsoft-Windows-Sysmon/Operational EventCode=1 Image="*powershell.exe" (CommandLine="*-EncodedCommand*" OR CommandLine="*FromBase64String*") | table _time, host, User, CommandLine, ParentImage

Detect T1003.001 (Credential Dumping / LSASS) in Splunk

index=endpoint sourcetype=XmlWinEventLog:Microsoft-Windows-Sysmon/Operational EventCode=10 TargetImage="*lsass.exe" | table _time, host, SourceImage, GrantedAccess, User
4.3 Network Reconnaissance & Port Scanning ▾

Nmap Scan from Kali

# Full port scan of entire lab subnet nmap -sV -sC -O 192.168.10.0/24 -oN lab_scan.txt # Aggressive scan of Windows target nmap -A -T4 192.168.10.30

Detect Network Scan in Splunk (Sysmon Event ID 3)

index=endpoint EventCode=3 | stats dc(DestinationPort) as unique_ports, count by SourceIp, DestinationIp | where unique_ports > 20 | sort -unique_ports

5.1 Build Alert Rules (Saved Searches) ▾

Alert 1 — Brute Force Detection (Account Lockout Threshold)

index=endpoint EventCode=4625 | bucket _time span=5m | stats count by Account_Name, IpAddress, _time | where count > 10

Save as Alert → Trigger: count > 10 → Action: Send Email / Slack webhook

Alert 2 — New Admin Account Created (Persistence)

index=endpoint (EventCode=4720 OR EventCode=4728) | table _time, host, Subject_Account_Name, Target_Account_Name, Group_Name

Alert 3 — PowerShell Encoded Command Execution

index=endpoint EventCode=1 CommandLine="*-EncodedCommand*" OR CommandLine="*-enc *" | table _time, host, User, ParentCommandLine, CommandLine

Alert 4 — Suspicious Scheduled Task Creation

index=endpoint EventCode=4698 | rex field=Message "Task Name:\s+(?<task_name>[^\n]+)" | table _time, host, User, task_name, Message

Alert 5 — LSASS Access (Credential Dumping)

index=endpoint EventCode=10 TargetImage="*\\lsass.exe" GrantedAccess IN ("0x1010", "0x1410", "0x147a") | table _time, host, SourceImage, TargetImage, GrantedAccess, User

5.3 Practice Incident Response Workflow ▾

SOC Analyst Investigation Checklist (per Alert)

  • Triage: Is this alert a true positive, false positive, or benign? Check context
  • Scope: Which host? Which user? What time window? Single event or pattern?
  • Pivot: From the host, search all events around the same time ±15 minutes
  • Process Tree: Use Sysmon Event ID 1 to trace parent→child process chain
  • Network: Did the compromised host make outbound connections? (Event ID 3)
  • Persistence: Were scheduled tasks, registry keys, or new accounts created?
  • Lateral Movement: Did the attacker log into other hosts? Check Event ID 4624/4648
  • Document: Write up a mock incident report with timeline, IOCs, and remediation

SPL — Full Investigation Pivot from a Suspicious Host

index=endpoint host=WIN-TARGET earliest=-1h latest=now | eval event_type=case(EventCode=1,"Process",EventCode=3,"Network",EventCode=4625,"FailedLogon",1=1,"Other") | stats count by event_type, User, EventCode | sort -count

6.1 Threat Hunting with SPL ▾

Hunt 1 — Living off the Land Binaries (LOLBins)

index=endpoint EventCode=1 Image IN ("*\\certutil.exe", "*\\bitsadmin.exe", "*\\mshta.exe", "*\\regsvr32.exe", "*\\rundll32.exe", "*\\wmic.exe") | stats count by Image, CommandLine, User, host | sort -count

Hunt 2 — Rare Parent-Child Process Pairs (Anomalous Execution)

index=endpoint EventCode=1 ParentImage="*\\winword.exe" OR ParentImage="*\\excel.exe" | stats count by ParentImage, Image, CommandLine, host | where count < 5

Hunt 3 — DNS Beaconing (C2 Indicators)

index=endpoint EventCode=22 | bucket _time span=1h | stats count by QueryName, _time, host | stats stdev(count) as stddev, avg(count) as avg_count by QueryName | where stddev < 2 AND avg_count > 10 | sort stddev

Hunt 4 — Long-Running Processes with Network Activity

index=endpoint EventCode=3 | stats dc(DestinationIp) as unique_ips, sum(bytes_out) as total_bytes by Image, host | where unique_ips > 50 OR total_bytes > 1000000 | sort -unique_ips
6.2 Tune Alerts — Reduce False Positives ▾
  • Add allowlists to searches: `NOT User IN ("SYSTEM", "LOCAL SERVICE", "NETWORK SERVICE")`
  • Tune Sysmon config — add `onmatch="exclude"` filters for known benign processes in SwiftOnSecurity XML
  • Use lookup tables in Splunk to whitelist known-good hashes, IPs, and domains
  • Track false positive rate: every alert fired should be reviewed and documented
  • Adjust alert thresholds based on your lab's baseline noise levels
# Create a whitelist lookup table # Settings → Lookups → Lookup Table Files → Upload: whitelist_processes.csv # Then in SPL: | lookup whitelist_processes.csv Image as Image OUTPUT is_whitelisted | where NOT is_whitelisted="true"
6.3 Add pfSense Firewall & Network Logs ▾
  • Add a pfSense VM as the network gateway for your lab — it replaces the simple NAT
  • Configure pfSense to forward firewall logs to Splunk via syslog (UDP 514)
  • Install Splunk Add-on for pfSense for proper field extraction
  • Now you can detect: port scans, blocked outbound connections, C2 traffic patterns, DNS over alternative ports
  • Layer with Sysmon + Windows Security logs for full kill-chain visibility
6.4 Sigma Rules & Detection Engineering ▾
  • Sigma is a generic YAML-based detection rule format — vendor agnostic, community-maintained
  • Convert Sigma rules to SPL using pySigma with the Splunk backend
  • Repository: github.com/SigmaHQ/sigma — thousands of production-grade rules
  • Write your own Sigma rule for every attack you successfully simulate, then convert it to a Splunk alert
# Install pySigma pip install pysigma pysigma-backend-splunk pysigma-pipeline-sysmon # Convert a Sigma rule to SPL sigma convert -t splunk -p sysmon sigma_rule.yml

Example Sigma Rule — Encoded PowerShell

title: Suspicious Encoded PowerShell id: abc123 status: experimental logsource: product: windows service: sysmon detection: selection: EventID: 1 Image|endswith: '\powershell.exe' CommandLine|contains: - '-EncodedCommand' - 'FromBase64String' condition: selection level: high tags: - attack.execution - attack.t1059.001
